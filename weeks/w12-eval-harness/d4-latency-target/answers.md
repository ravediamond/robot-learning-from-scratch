# Model answers

1. Measure on the target with its power mode and clocks fixed (`nvpmodel`, `jetson_clocks`), after warm-up (first calls compile kernels, allocate, autotune), synchronising the GPU before stopping the timer (`torch.cuda.synchronize()` or events), with the real preprocessing and camera input rather than a cached tensor, for long enough to see thermal throttling, while the rest of the stack (camera, logging) runs. Separate preprocessing, model, postprocessing; report the end-to-end observation-to-action time too.
2. Control quality fails on the worst cases: one 200 ms freeze is a visible stop and a possible collision, and it disappears in a mean. A deadline-miss rate at the control period ties the number to what the robot experiences; p95/p99 and max show the tail; the mean only matters for throughput.
3. With latency L, period T, e actions executed per chunk and chunk length H: the next chunk is requested when a chunk starts, so it must arrive within e·T (no empty queue), and when it arrives ceil(L/T) of its actions refer to the past, so H ≥ ceil(L/T) + e. When they fail: shorten inference (smaller model, fewer flow steps, quantisation, TensorRT), lengthen chunks, execute more actions per chunk (less reactive), or overlap smarter (start the request earlier, RTC).
4. Sync stops and starts the arm: jerky motion, objects disturbed at each pause, longer episodes and more timeouts, which a success-rate table attributes to the policy. Async keeps motion continuous but switches between chunks predicted from different observations: discontinuities at the seam, and actions computed from an observation up to L old. Both change the success rate, so the execution mode is part of the method and must be fixed and reported.
5. RTC treats the switch to a new chunk as inpainting: while generating the next chunk, the actions that will be executed during inference are fixed to the current chunk's, and the rest is generated to be consistent with them (guided denoising with a soft mask over the overlap). It removes the seam discontinuity of naive async switching and tolerates longer latencies without starving or jerking.
6. Power mode and clocks; thermal throttling; the model running in fp32 instead of fp16, or partly on CPU (unsupported ops falling back); preprocessing on CPU (image resize, normalisation, JPEG decode) and data copies between CPU and GPU; batch or sequence size differences (padding to a larger context); kernels not autotuned (first-call effects, no warm-up); a different torch/CUDA build without the fused attention kernel. Profile before optimising.
