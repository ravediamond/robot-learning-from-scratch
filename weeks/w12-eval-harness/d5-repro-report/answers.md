# Model answers

1. Code version (git SHA and dirty flag), checkpoint fingerprint and where it is stored, dataset name and revision (hub revision or content hash), full config (resolved, not just overrides) and its hash, policy execution settings (chunk length, actions executed per chunk, sync/async, flow steps, temperature), hardware and firmware (device, power mode, camera models and exposure, servo firmware), package versions (torch, CUDA, LeRobot, drivers), protocol version and start-configuration map, random seeds, operator. Commonly forgotten: execution settings, camera settings and the calibration file of the arm.
2. Names and revisions can be overwritten, mirrored or silently re-uploaded, and a "best.pt" in the wrong folder is a classic. The fingerprint is computed from what is actually loaded into the model, so the launcher can refuse a mismatch and the report can prove which weights produced each number.
3. Diff the manifests first (code, weights, config, execution mode, packages, hardware). Then the protocol: start configurations, schedule, operator, success criteria. Then the environment: lighting, objects, calibration drift, servo temperature and battery. Check the statistics: is 12 points outside the noise for that n (two Wilson intervals at 50 rollouts overlap easily)? Rerun a small blocked A/A comparison (same checkpoint twice) to measure the setup's variance.
4. Per policy: n, success with a 95% CI, the main failure causes as rates with CIs, latency p50/p95 on the target, execution settings. Next to it: the protocol (starts, schedule, blinding, criteria), the pre-registration and what deviated from it, the minimum detectable difference, the pairwise tests with Holm, the manifest of each run, and videos of typical successes and failures.
5. Keep a frozen reference policy and re-run it in every session as a calibration arm; version the protocol and the setup; keep the same start map; record manifests; and when something changes, run an overlap session with old and new setups to measure the shift instead of assuming it is zero.
6. Reproducible: every number traces to code, data, weights and settings through a manifest, and the evaluation reruns from one command. Measurable: success with uncertainty, fair paired protocols, failure causes, and the minimum effect the experiment can see. Deployable: latency and deadline behaviour measured on the robot's computer, with the execution mode as part of the method. I build that harness, and I have used it on my SO-101 with four policies.
