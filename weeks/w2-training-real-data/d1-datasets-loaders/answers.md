# Model answers

1. One per frame: every timestep is a training state, so the policy learns every situation; long episodes contribute more samples (often fine: they contain more decisions; but slow/hesitant demos get over-weighted). One per episode then a random t inside: each episode equally likely, short episodes over-represented per frame. Choose by what you want weighted; say it.
2. Repeat last: the target says "hold the final pose", consistent with what the robot should do at the end, and the mask removes it from the loss anyway. Zeros: if not masked, teaches "move to joint 0" at the end of every episode (dangerous). Dropping windows: loses the most important frames (the end of the task: release, retreat). Repeat + mask is the LeRobot default for a reason.
3. The last H−1 frames of each episode (e.g. 49 of ~340 with H=50, ~15%) get targets that jump to the next episode's start pose. The policy learns "near the end, move toward some random new pose". Loss looks normal because those targets are a small fraction and are themselves learnable-ish noise; it shows up as weird motion at the end of the task (after the place).
4. Each worker is a separate process with a copy of the RNG state: all workers can produce the same augmentation sequence, or (with numpy) the same random crops each epoch. Fix: `worker_init_fn` that seeds numpy/random from `torch.initial_seed()` (which PyTorch sets per worker), and a seeded generator for the sampler.
5. Measure first (profile data time vs step time). Then: num_workers > 0 + pin_memory + persistent_workers; decode videos once to a cache of smaller frames (resize/crop offline); prefetch; avoid Python per-frame work (vectorize, read whole episodes); keep data on the GPU if it fits. Data-bound GPUs are the most common waste in robot training.
6. Balance: the rare task gets enough gradient, otherwise the policy may never succeed at it. Don't balance: 10 episodes repeated 9× more often → overfitting to those 10 demos, and the true deployment mix may be 90/10. Decision: balance partially (e.g. weights ∝ count^0.5) and evaluate per task; collect more data for the rare task if it matters.
