# Model answers

1. The unit of variation you want to generalise across, grouped so that nothing correlated crosses the split. Session (lighting, object placement, camera pose of that day) by default. Operator when claiming robustness to demonstration style. Station when the policy will run on new robots. Object set when claiming generalisation to new objects. Report several held-out axes rather than one random split.
2. Resample trajectories (state, action) to fixed length and compare (RMS, DTW for timing differences), or compare embeddings of the first and last frames plus the trajectory; cluster within a tolerance. Keep one per cluster for evaluation splits; for training, down-weight rather than delete (repeats can be intentional), and never let a cluster cross the split.
3. Exact content (per-episode content hashes → a dataset fingerprint), the curation rules and their version (QA thresholds, ledger state), the split assignment, the source datasets and their revisions with mixture weights, the preprocessing and normalisation statistics, and the code version that produced it. A hub revision id helps but does not prove content.
4. A ledger keeps every decision visible and reversible: you can restore episodes when a check was wrong, reproduce any past version by replaying the ledger, audit why the dataset shrank, and measure the effect of a rule by training with and without it. A filtered copy loses the reasons and multiplies storage.
5. Task(s) and success criteria, robot and its calibration, cameras and their placement, fps, number of episodes and hours, operators (count, experience), sessions and conditions (lighting, objects, positions), collection protocol, known issues and quarantined data, QA checks applied, splits, licence and consent, intended use and limits, and the dataset fingerprint.
6. To check training health (overfitting, broken normalisation, a regression in a data pipeline) and to compare runs on the same data quickly. It is a smoke test, not a selection criterion: model selection still needs closed-loop evaluation, ideally on held-out sessions of the real robot.
