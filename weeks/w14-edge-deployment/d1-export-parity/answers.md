# Model answers

1. Everything between the robot's raw observation and the motor command that must be identical in training and deployment: image preprocessing (resize, crop, normalisation), state normalisation, the model, action unnormalisation, and for chunked policies the chunk-selection logic or at least its parameters. Usually missing: normalisation stats (kept in the data pipeline), image preprocessing (done in Python with a different library), and postprocessing such as gripper thresholds or clipping.
2. Record a few thousand real observations from the robot (not random tensors: real ranges matter), run them through PyTorch in eval mode and through the runtime, compare outputs (max and percentile absolute error) and, more important, the resulting actions in joint units. fp32: ~1e-6. fp16: ~1e-3 relative is normal; check the effect on actions and closed-loop success. int8: no fixed tolerance: judge on action error and on a short closed-loop evaluation.
3. TorchScript: legacy, mostly avoid. ONNX: the portable interchange format and a good runtime on CPU; the route into TensorRT. TensorRT: the fastest on Jetson GPUs (fp16/int8, fused kernels), engines built per device and version. `torch.compile`: speedups while staying in PyTorch, useful when export is hard (dynamic control flow), heavier runtime. In practice: PyTorch first to measure, TensorRT for the networks that dominate latency.
4. Not the network: the inputs. Camera preprocessing differences (colour order, resize interpolation, exposure), the observation timing (stale frames, the lag between state and image), unit or joint-order mismatches, the control loop (rate, chunk execution, interpolation between actions), and the hardware (calibration). Log the observations the deployed policy actually sees and replay them through the training pipeline.
5. Source checkpoint fingerprint, training run id and git SHA, dataset fingerprint, normalisation stats version, exporter and runtime versions, precision, input/output names and shapes, parity results, execution settings (chunk, rate), and who approved it.
6. Large graphs with attention, KV caches, dynamic sequence lengths and an iterative sampler (flow steps in a Python loop). Split it: export the backbone (prefix encoding, run once per observation) and the action head (run per flow step) as separate engines with fixed shapes; keep the flow loop in the host code or unroll a fixed small number of steps; use fp16 and fused attention; cache the prefix. Measure each part's latency before optimising.
