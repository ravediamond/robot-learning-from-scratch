# Model answers

1. Evaluation passed (pre-registered rule) → artifact built, exported, parity checked, fingerprinted, approved → shadow mode on a few robots (disagreement review) → canary on ~5% with a minimum number of hours and the rollback test → 25% → 100%, each stage with its own minimum duration and the same automatic rollback rule; the previous version stays installed and switchable.
2. Where the new policy would act differently from the deployed one, on the real distribution of observations, at no risk: good to find situations to review and to catch broken artifacts (huge disagreement everywhere). It cannot tell you which one is right or what happens after the first different action (the closed-loop consequences): only executing it can.
3. Interventions per robot-hour, task success or throughput per hour, safety-filter events (rate limits, stale, e-stops), failure-detector alarms, latency percentiles on the device, and hardware health. Rollback triggers: a significant rise in interventions or safety events, any serious safety incident (immediate, no statistics), latency budget violations.
4. Intervention counts are small Poisson numbers: eyeballing either rolls back good models on noise (wasting the improvement) or keeps bad ones because "it is early". A pre-registered test with a minimum exposure makes the decision explicit; choose α by the cost: a false rollback costs a delay, a missed regression costs field failures, so tolerate more false rollbacks for safety metrics.
5. Do not swap mid-motion: finish or abort the current task to a safe pose (or let the operator take over), then load the previous version at a task boundary; the runtime supports two loaded versions or a fast swap with the artifact cached locally; log the switch.
6. Declarative desired state per robot (software, firmware, model fingerprint, calibration version), an agent on each robot reporting its actual state, reconciliation (the Kubernetes idea), version pinning with staged updates, and drift alerts; every log line carries the versions so field results can be grouped by configuration.
