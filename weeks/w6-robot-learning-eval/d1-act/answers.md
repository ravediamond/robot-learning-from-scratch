# Model answers

1. The variation in how a demo was executed that the observation does not determine (operator style, which of several valid paths). At test time one consistent, "average style" behaviour is wanted, and z = 0 is the prior's mean: deterministic and in the high-density region of the latent.
2. Large beta: the KL pushes q(z|x) to the prior, mu std ≈ 0, z carries no information: the decoder alone decides (posterior collapse). Small beta: z carries the side, but the aggregate posterior may not match N(0, I), so z = 0 or prior samples land in "holes". Seeds of the same setting can differ by tens of points in collision rate: one run proves nothing; report several seeds and intervals.
3. The L1 optimum is a median; for a symmetric 50/50 split any point between the modes is a median, and small asymmetries or optimisation dynamics push the network to one side for a given observation. It is not reliable: the side can flip between nearby observations (dithering) or settle in the middle. Use a generative head if multimodality matters.
4. Temporal ensembling: inference every step (needs the policy to run at 30 Hz: not with 300 ms), smoothest, reacts gradually. Open-loop chunks with replanning: cheap, jumps at boundaries, reacts every H_exec steps. RTC/async: hides the 300 ms latency by generating the next chunk while executing, consistent boundaries. For 300 ms on an SO-101: async chunks (+ RTC-style prefix freezing), not ensembling.
5. With all-equal weights it executes the mean of actions planned 0..H−1 steps ago: a lag of about (H−1)/2 steps, i.e. ~25 steps (~0.8 s) for H = 50 at 30 Hz. Averaging also smooths, so nothing looks wrong: just late.
6. ACT with 50 demos of a mostly unimodal pick-and-place: data-efficient, fast, LeRobot default, temporal ensembling gives smooth motion. Switch to Diffusion Policy (or a flow head) if a pre-registered eval shows mode-averaging failures (hesitation, collisions between alternatives) or if success plateaus with more data. Measure on the same 20 start layouts with CIs.
